# План работы на двоих

**А отвечает за выбор и порядок материалов. Б отвечает за пользовательский сценарий и независимую проверку выдачи.** В начале обе ветки берут общий контракт и фикстуры из `main`. Для разработки интерфейса Б подключает `app.ui.stub.recommend`. Для разработки алгоритма А вызывает свою функцию напрямую.

## Общий контракт

```python
recommend(catalog, profile, history, limit) -> RecommendationResult
```

| Данные | Соглашение |
| --- | --- |
| `catalog` | Последовательность `Material` с уникальными `id`. У материала есть название и URL из каталога. Темы, описание, формат, доступ и признаки профиля могут отсутствовать. |
| `profile` | `Profile(stage, industry, goal, experience)`. Каждое поле опционально. `goal` принимает свободный текст. А и Б используют согласованные значения для выбора стадии, сферы и опыта в интерфейсе. |
| `history` | Последовательность `InteractionEvent` одного пользователя. Для холодного старта передаётся `()`. В стартовом формате поддержаны `view`, `click`, `complete`. Время опционально и передаётся с часовым поясом, когда известно. События по отсутствующим в каталоге ID игнорируются. |
| `limit` | Верхний предел количества карточек. Для пустого каталога или `limit <= 0` список пуст. |
| `result.items` | Карточки по убыванию приоритета. Каждый ID встречается один раз и присутствует в каталоге. В карточке есть `reason` и `next_step`. Интерфейс берёт название и URL из каталога по ID. |
| `result.ordering_reason` | Короткое объяснение порядка всей непустой выдачи. Например, сначала практический шаблон под текущую задачу, затем материал для углубления. |
| `result.follow_up_question` | Опциональное уточнение, которое можно показать вместе с общей подборкой. Б подставляет ответ пользователя в профиль и заново вызывает `recommend`. |

`load_catalog(path)` принимает нормализованный JSON с полями `Material`. `load_history(path)` принимает нормализованный JSON-журнал с `material_id`, опциональным `kind` и опциональным временем `occurred_at` в формате ISO 8601. Примеры обоих форматов есть в `fixtures/`. Преобразование сырой выгрузки в эти форматы принадлежит А. При необходимости изменить общий контракт А и Б сначала договариваются о новых полях, после чего А делает один отдельный коммит, который забирают обе ветки.

## Роль А — данные, ранжирование и презентация

**Ветка** `feat/recommender`. **Файлы** `app/catalog/`, `app/recommender/`, `tests/recommender/`, `docs/presentation/`. А владеет `app/contracts.py` и общими фикстурами после согласования изменений с Б.

| Задача | Результат и проверка |
| --- | --- |
| **А1. Разобрать выгрузку** | Перечислить файлы, идентификаторы материалов, поля каталога и доступные события. Проверить заполненность темы, стадии, сферы, опыта и ссылок. Сопоставить события с ID материалов. Отдать Б описание данных и инструкцию подключения для README. |
| **А2. Нормализовать данные** | Загрузить реальный каталог и, при наличии, журнал одного пользователя в типы из контракта. Зафиксировать правила обработки пропусков, повторяющихся ID и неизвестных видов событий. Сохранить совместимость со стартовыми фикстурами. |
| **А3. Сделать подбор** | Начать с понятного ранжирования по теме и текущей задаче, затем учитывать стадию, сферу, опыт и доступную историю. Проверить пары профилей, где меняется один признак. Слабый исторический сигнал должен дополнять текущую задачу. |
| **А4. Сделать холодный старт и выдачу при слабом совпадении** | При пустом профиле подобрать доступные вводные или практические материалы. При одной известной задаче дать подборку по ней. Если точного совпадения нет, вернуть более общий материал, маршрут или короткое уточнение. В стартовой выдаче дать первый применимый шаг и понятное продолжение, ради которого можно вернуться на платформу. |
| **А5. Объяснить результат** | Вернуть причину места материала в подборке, его следующий шаг и объяснение порядка всей выдачи. Для платных материалов использовать краткое описание пользы и исходную ссылку. Экспортировать `app.recommender.recommend` по контракту. |
| **А6. Подготовить защиту и измерение эффекта** | Включить в PDF проблему, аудиторию, архитектуру, пользовательский путь, примеры, ограничения и результаты сравнения от Б. Предложить A/B-тест после внедрения с одинаковым интерфейсом в обеих группах. Сравнить долю пользователей, совершивших покупку в согласованном окне, например 14 дней. Дополнительно измерить переходы к материалам и число дней с посещением платформы. |

## Роль Б — интерфейс, оценка и выпуск

**Ветка** `feat/demo-evaluation`. **Файлы** `app/ui/`, `app/__main__.py`, `evaluation/`, `tests/ui/`, `tests/test_starter.py`, `README.md` и корневые файлы запуска. Изменения корневых зависимостей делает Б по списку от А.

| Задача | Результат и проверка |
| --- | --- |
| **Б1. Сделать пользовательский путь** | Короткий опциональный онбординг с кнопкой «Пропустить». Можно задать одну задачу и сразу увидеть подборку. Форму и карточки сначала проверить с заглушкой. |
| **Б2. Показать выдачу и историю** | Показать объяснение порядка, карточки с причинами и следующими шагами, уточнение при наличии и переход по исходному URL. Предусмотреть демосценарии с журналом и без него. Журнал передавать в `recommend` через тот же контракт. |
| **Б3. Подготовить бейзлайн и разметку** | Реализовать ранжирование только по совпадению темы. Составить набор профилей и отметить подходящие ID до просмотра результатов алгоритма А. Включить профили с пустой историей, одинаковой темой при разной стадии, синтетическими событиями и запросом без точного совпадения. |
| **Б4. Сравнить методы** | Использовать один каталог, одну разметку и одинаковый `limit=3` для обоих методов. Посчитать долю профилей с хотя бы одним релевантным материалом в топ-3. Передать А таблицу выдач и примеры, где алгоритм выиграл или проиграл. Метрику качества выдачи и будущую конверсию в презентации показать отдельно. |
| **Б5. Собрать запуск и интеграцию** | Подготовить Dockerfile, `compose.yaml`, `.dockerignore`, `env.example`, закреплённые зависимости и инструкцию запуска. Подключить `app.recommender.recommend` в точке входа и проверить сквозные сценарии. А проверяет чистый запуск по инструкции со своей машины. |

## Три сценария из приложения 2 для обязательной репетиции

| Проверка | Ожидаемый результат |
| --- | --- |
| **1. Новичок указывает задачу «продвижение бизнеса»** | Истории нет. Появляется стартовая подборка из каталога. Понятно, почему первый материал выше остальных и что сделать после него. |
| **2. Журнал есть или отсутствует** | Прогнать один профиль с пустой историей и с синтетическими событиями. При пустой истории подборка даёт применимый первый шаг и продолжение обучения. Для известного полезного сигнала показать, что именно изменилось в порядке или рекомендациях и почему. |
| **3. Данных мало или точного совпадения нет** | Например, профиль неполный, а запрос выходит за пределы каталога. Система даёт уместное уточнение, более общую подборку или маршрут из имеющихся материалов. Объяснение соответствует доступным данным. |

Для стартовой фикстуры удобно проверять различия на `marketing-first-sales`, `marketing-repeat-sales` и `marketing-service-leads`. Для проверки журнала используйте `fixtures/history.demo.json`. Для проверки пропусков в карточке используйте `operations-week-plan`.

## Порядок работы в Git

Оба участника берут общий стартовый коммит из [HackatonAlfa](https://github.com/Cheburek254/HackatonAlfa). Из актуальной `main` каждый создаёт свою ветку.

```powershell
git switch main
git pull --ff-only origin main
# Участник А выполняет:
git switch -c feat/recommender
# Участник Б вместо этого выполняет:
# git switch -c feat/demo-evaluation
```

1. **На старте** А и Б сверяют типы и поля интерфейса. Пока А изучает реальные данные, Б использует синтетический каталог.
2. **До интеграции** А показывает рабочий вызов `recommend` напрямую. Б показывает полный пользовательский путь с заглушкой, бейзлайн и заранее размеченные профили. Каждый коммитит только свои файлы.
3. **При интеграции** сначала принять ветку А в `main`, затем Б подтягивает `main` в свою ветку и заменяет заглушку в точке входа. Б прогоняет сравнение и тесты перед слиянием. Результаты сравнения передаются А для презентации отдельным коммитом.
4. **Перед сдачей** оба проходят три сценария, сверяют инструкцию Docker-запуска и ссылки. На первом слайде PDF нужен порядок проверки и ссылка на репозиторий при сдаче через него. Исходную выгрузку и ключи храните локально. Для приватного репозитория, если он используется для сдачи, предусмотрите доступ аккаунту жюри `hack-and-change-2026`.
